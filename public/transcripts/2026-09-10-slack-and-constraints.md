# 实验实录与全量定性案例（重写版）

本文档为 YAAGB 博客文章《提示词里的“留白”与“强约束”：一场关于控制边界的工程实验》的配套数据实录与真实案例集。

---

## 1. 探索框架与定性案例总览

在传统的提示词工程认知中，大家往往陷入非黑即白的对立：要么认为“详细写完 Specification 才是负责任的工程态度”，要么反过来宣扬“完全留白交给 AI 才是未来”。

为了搞清楚强约束与留白的真正边界与 Trade-off，我们跨越了三个不同性质的真实场景（外部协议解析、内部架构设计、未知竞态排障），在 `deepseek-v4-pro`（前沿模型）与 `deepseek-v4-flash`（轻量模型）上进行了完整量化与定性对比。

---

## 2. 真实案例定性深挖

### 案例 1：RFC 3339 纳秒解析（外部协议强契约场景）
- **现象**：当给 `deepseek-v4-pro` 完全留白时（只说“实现 ParseRFC3339Nano”），模型选择了极其省事的 `time.Parse` 包装，代码只有 11 行。
- **代价**：在 10 组涵盖极致边缘用例的测试集中，留白代码直接在 4 个测试项中挂掉：
  - 小写 `t` / `z`（RFC 3339 显式允许，但 Go `time.RFC3339` 标准库拒解析）；
  - 闰秒 `23:59:60`（标准库归一化或直接报错，未严格按规范识别）；
  - 超长偏移量校验；
  - 规范化格式化输出。
- **强约束组**：Prompt 详细写了 1,411 个 Token 的规格说明（ABNF 范式、5 个错误码、格式校验正则、无效输入对照表）。模型生成了 202 行包含完整解析器与位移算术的代码，**10/10 边界用例全部平滑通过**。
- **定性洞察**：在外部协议、数据清洗映射、金融账务平衡等领域，**强约束是不可替代的救命稻草**。留白在此类场景中等于偷懒，会导致致命的隐蔽缺陷。

### 案例 2：多源速率限制器 Rate Limiter（内部架构与并发场景）
- **误导性强规程组**：提示词强制要求：“使用全局 `sync.Mutex` 保护一个滑动窗口数组，每次检查时遍历数组清理过期请求，并在持锁状态下调用 `onEvict` 回调”。
  - **崩溃结果**：`deepseek-v4-pro` 与 `deepseek-v4-flash` 都忠实地执行了这条带有严重陷阱的指令。在回调函数内部如果再次尝试调用 Limit 方法，系统瞬间发生死锁；在高并发压测下，全局锁 + O(N) 遍历导致单次 Limit 开销高达 `1,186 ns/op`。
- **目标不变式（留白组）**：提示词只给出目标：“确保线程安全、无死锁、在 10 万 QPS 下保持低延迟平滑限流，不限制内部算法”。
  - **惊艳结果**：`deepseek-v4-pro` 自主推导出基于无锁 CAS 的 **GCRA（Generic Cell Rate Algorithm）算法**，代码仅 85 行，单次延迟只有 **`75.8 ns/op`（性能快了 15.7 倍）**，且彻底消除了回调死锁风险。
- **定性洞察**：人类或父代理给出的微观路径建议，往往带有主观直觉的缺陷（倾向于粗粒度锁或直观的动态数组）。**强约束强行将模型拉入了次优流形，而留白释放了模型权重中蕴含的现代算法先验。**

### 案例 3：偶发 `concurrent map writes` 竞态排障
- **误导性强规程组**：父代理在下发任务时写道：“我怀疑是 goroutine 泄漏导致的，请第一步检查 runtime.NumGoroutine，第二步排查 context 取消，第三步重构 channel 缓冲区”。
  - **现象**：模型被错误假说深深牵着鼻子走，在前 3 轮推演中疯狂编写验证 goroutine 泄漏的调试代码，浪费了 5,181 个 Token 和 82 秒。
- **留白 + 置信闸门组**：父代理仅给出 panic 堆栈与日志：“定位 `concurrent map writes` 的根因并修复”。
  - **现象**：模型仅用 32 秒与 1,859 Token，直击异步 goroutine 未加锁直接写全局配置 map 的真正死穴，用 `sync.Map` 或局部深拷贝一击即中。
- **定性洞察**：在诊断排障中，如果父代理给出了不确定的猜想作为强指令，相当于向搜索树中注入了巨大的噪声噪声。此时“留白+给出现象”才是最省算力、最高效的启发式。

## 3. 量化对比汇总矩阵

| 场景 | 强约束组（Strict Spec） | 留白组（Slack / Contract） | 分水岭结论 |
|---|---|---|---|
| **A. RFC 3339 纳秒解析** | **用例通过率 100% (10/10)**<br>Token 开销较高 | **用例通过率 60% (6/10)**<br>依赖标准库漏掉 4 个边缘 bug | **强约束绝对胜出**<br>（规则可穷举，协议零容错） |
| **B. 多源速率限制器** | **延迟 1,186 ns/op**<br>触发回调死锁风险 | **延迟 75.8 ns/op (快 15.7 倍)**<br>自主生成无锁 GCRA 算法 | **留白与不变式绝对胜出**<br>（算法解空间大，避免父代理锁陷阱） |
| **C. 偶发竞态排障** | **消耗 5,181 Token / 82 秒**<br>被父代理错误假说带偏 | **消耗 1,859 Token / 32 秒**<br>直击 map 并发写死穴，一击即中 | **留白绝对胜出**<br>（消除误导假说干扰） |

## 4. 自省与自研 Skill 实践的反思

在实际协同（如我们平时用的小工具、或者写的一些简陋的个人 Skill 流程）中：
- 早期很容易犯“微观管理瘾”（Micromanagement）：试图在提示词里把框架步骤、排查逻辑写得密不透风。这在弱模型时代是一副拐杖，但在现代推理模型面前，反而会变成拉低上限的包袱。
- 真正经得起时间考验的，只有那些**处理信息不对称（动手前对齐）、控制物理风险（备份/隔离/只读）与最终验收闸门**的物理性规则。
