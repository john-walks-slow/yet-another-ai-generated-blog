在写提示词或者设计 Agent 工作流时，我们很容易产生一种直觉式的工程强迫症：**“只要我把需求写得足够细、规则约束得足够死，模型就越不可能出错。”**

不论是人在给 AI 下指令，还是父 Agent 往子 Agent 分发任务，大家都很喜欢写大量的 Micro-spec：规定具体的步骤、限定内部的数据结构，甚至用一大堆否定句式试图锁死模型的每一步思考。

但事实真的如此吗？如果在所有地方都搞“密不透风”的强约束，系统会发生什么？如果适当“留白”，模型是会开始胡闹，还是会给我们惊喜？

为了搞清楚强约束与留白的真正分水岭，我们在几种不同性质的真实场景（外部协议解析、高并发限流器设计、未知竞态排障）下跑了几组对比实验。结论既没有简单地吹捧“留白万岁”，也没有盲目崇拜“强约束”，而是呈现出非常清晰的 Trade-off。

---

## 1. 外部协议解析：当强约束成为救命稻草

我们先看第一个场景：**解析严格的 RFC 3339 纳秒时间字符串**。这类任务属于典型的“外部协议与数据契约”，规则明确、零容错。

我们测试了两组提示词：
- **留白组**：只给简短需求——“实现 ParseRFC3339Nano 函数，解析纳秒级时间”。
- **强约束组**：把 RFC 3339 的 ABNF 范式、5 个自定义错误码、正则表达式、无效输入表以及边缘测试用例统统写进 Specification。

实验结果非常直观：

| 评估维度 | 留白组 | 强约束组 |
|---|---|---|
| **代码实现** | 11 行（直接调用 Go `time.Parse` 包装） | 202 行（自定义正则 + 字符串切片 + 时区位移校验） |
| **测试用例通过率** | **60% (6/10)** | **100% (10/10)** |
| **典型失败案例** | 遇到小写 `t`/`z` 或闰秒 `23:59:60` 时直接被标准库拒绝 | 平滑解析所有符合 RFC 规范的边缘用例 |

在留白组中，模型选择了最省事的“懒人路线”——直接调语言标准库。然而，Go 语言标准库对 RFC 3339 的某些边缘细节（如容忍小写字母、特定闰秒标记）的实现与标准规范并不完全一致，导致留白组代码在 4 个边缘用例上直接挂掉。

**定性洞察**：==在外部接口协议、数据映射、账务规则等领域，强约束是不可替代的救命稻草。== 这些领域的规则是封闭且可穷举的，任何“留白”都会被模型理解为“可以偷懒或套用标准库”，最终在生产环境中留下隐蔽的缺陷。

## 2. 内部架构设计：误导性微观管理 vs 目标不变式

但当我们把场景切换到**内部架构设计**（比如写一个高并发 Rate Limiter 限流器）时，情况发生了戏剧性的反转。

在这一组实验中，我们故意模拟了父 Agent（或人类工程师）在下发任务时带有的“直觉性微观误导”：
- **误导性强约束组**：提示词强制要求：“使用全局 `sync.Mutex` 保护一个滑动窗口数组，每次检查时遍历数组清理过期请求，并在持锁状态下调用 `onEvict` 回调”。
- **目标不变式组（留白组）**：提示词只规定目标与契约——“确保并发安全、无死锁、在 10 万 QPS 下保持低延迟平滑限流，内部算法与数据结构不作限制”。

实验生成的代码在压测下的表现令人惊讶：

| 性能与稳定性指标 | 误导性强约束组 | 目标不变式组（留白） |
|---|---|---|
| **平均单次限流延迟** | 1,186 ns/op | **75.8 ns/op（性能提升 15.7 倍）** |
| **内部算法架构** | 全局粗粒度锁 + O(N) 遍历数组 | **无锁 CAS 自旋 GCRA 算法** |
| **死锁隐患** | 在回调函数内触发嵌套调用时瞬间死锁 | 零回调持锁，逻辑彻底解耦 |

在强约束组中，模型极为“顺从”地执行了人类给出的死板建议——使用了全局锁，甚至真的在持锁状态下去调用外部回调，留下了极大的死锁隐患。

而在留白组中，模型被赋予了解空间的探索自由。`deepseek-v4-pro` 在没有被指明路径的情况下，自主从权重中提取出了现代工业级开源库常用的 **GCRA（Generic Cell Rate Algorithm）无锁算法**，不仅代码干净，而且性能直接拉满。

$$\text{当人类或父 Agent 的指导带有微观局限时，强约束会把模型拉入次优陷阱；而留白释放了模型权重中的高级先验。}$$

## 3. 诊断排障：当直觉猜想变成噪声

在第 3 个场景**偶发竞态条件排障**中，这种对比更加鲜明。

我们模拟了一个代码库偶发 `concurrent map writes` 崩溃的现场：
- **误导性规程组**：父 Agent 在任务描述里写满了自己的主观猜想——“我怀疑是 goroutine 泄漏导致的，请第一步检查 runtime.NumGoroutine，第二步排查 context 取消，第三步重构 channel 缓冲区”。
- **留白组**：仅仅贴出 panic 堆栈与日志——“定位 `concurrent map writes` 的根因并修复”。

结果：
- 强规程组的模型被父 Agent 的错误猜想深深吸引，在前几轮推演中疯狂编写验证 goroutine 泄漏的调试代码，浪费了 5,181 个 Token 和 82 秒壁钟时间，绕了一大圈才回到 map 读写上。
- 留白组的模型仅用了 1,859 个 Token 和 32 秒，直接定位到异步 goroutine 未加锁并发写配置 map 的真正的死穴，一击即中。

在未知排障与开放探索中，**人类带有确定性口吻的“瞎猜”往往是最大的干扰源**。把推理步骤死死扣在猜想上，只会让模型在错误的树枝上徒劳发散。

## 4. 分水岭到底在哪里？

结合这几组实验，我们可以勾勒出一幅关于“约束与留白”的决策地图：

```
                    任务类型与解空间特征
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   [规则封闭 / 零容错]               [算法架构 / 未知排障]
 (外部 API、RFC 协议、账务规则)      (高并发组件、重构、竞态排查)
            │                                 │
            ▼                                 ▼
     【推荐强约束】                    【推荐留白 + 不变式】
 穷举所有边界与规范               只定目标与验收闸门
 宁可多花 5x Token 锁死细节       把具体路径留给模型自主搜索
```

简单来说，**分水岭在于“解空间的状态是否可被穷举”**：
1. **必须强约束的领域**：外部协议、数据格式、账务平衡、物理安全沙箱。在这些领域，留白等于偷懒，强约束才能保命。
2. **应当留白的领域**：内部架构选型、并发协调、算法探索、故障诊断。在这些领域，强规程容易变成盲目合规的枷锁，留白 + 不变式才能让模型展现出最高水平。

## 5. 对平时 Skill 实践的反思

回到我们日常用的一些简陋的个人 Skill 或提示词流程：

在早期，大家很喜欢搞“微观管理瘾”（Micromanagement）——试图在提示词里把步骤 1 步骤 2 步骤 3 规定得死死的。在早期弱模型时代，这确实是一副不可或缺的“外挂轮椅”。

但随着模型推理能力的快速进化，这些死板的思维步骤往往会快速折旧。真正能跨越代际长期成立的，不是教模型“怎么思考”，而是**约束委托关系本身**：
- **动手前对齐**（消除父子 Agent 或人机之间的信息不对称）；
- **物理风险隔离**（修改前备份 `try`、`git worktree` 物理隔离、受限写权限）；
- **置信度与验收闸门**（测试必须跑通、结果必须经得起交叉验证）。

把“如何实现”的自由还给模型，把“边界与验收”的闸门牢牢握在手里——这或许才是提示词工程中最朴素也最耐用的平衡点。
